LexiAgent — Deterministic Contract Drafting

A contract drafting system that confines AI to structured field extraction and assembles every contract from a vetted clause library. The model never writes legal text. Output is a professional DOCX with embedded source citations, plus an interactive HTML artifact where every value traces back to the user's own words. Runs as an OpenAI-compatible API behind Open WebUI, scales horizontally on Kubernetes, and swaps between local Ollama and the Claude API with one environment variable.

The Technical Problem
1

Free-generation LLMs hallucinate

Letting a model write contract text means hallucinated clauses, drifting field names, and untraceable language. Acceptable for prototypes — not for documents people sign.

2

One-shot extraction guesses

Naive extractors fill missing fields with plausible-looking defaults. Without an evidence requirement, "we'll figure it out" becomes "the system invented a 5-year term."

3

No reusable, governed clause data

Vendor templates exist as Word documents. There's no structured, typed, versioned clause library that an assembler can select against — you build that yourself.

Architecture

Three zones, one rule: AI lives only in the extraction zone. Everything that ends up in the contract comes from the deterministic zone. The boundary between them is the schema — fields go in, clauses come out, and there's no path for model output to bypass the assembler.

How It Works
1

User describes the contract in Open WebUI

"We need a service agreement between GlobalTech Solutions and CleanPro Services for $3,500/month janitorial. Starting Feb 1, 2026. California law, mediation for disputes."

2

Provider-agnostic AI extraction

FastAPI routes the prompt to whichever extractor is configured — local Ollama (qwen3:4b) by default, or Claude via API for throughput. The extractor maps the prompt into the contract type's questionnaire schema. Every extracted value carries a quoted evidence span.

3

Follow-up loop for missing required fields

If a field has no evidence, it becomes a follow-up question — never a guess. The parser handles three answer formats: numbered, labeled, and line-by-line. Coverage on the live test suite is 99.7% after one follow-up turn.

4

RAG clause selection (always local)

For multi-variant clause families (Consulting / Employment / Service), nomic-embed-text embeddings score variants against the verified field context. Embeddings are cached as .npz files alongside the clause library. NDA clauses are deterministic (single canonical variant per type).

5

Deterministic assembly

Selected clauses get their placeholders algorithmically filled from verified fields, then stitched in fixed order from assembly_order_*.json. No LLM call in the assembly path. Same inputs, same contract — byte-for-byte reproducible.

6

DOCX + HTML artifact, both auditable

The DOCX is Times New Roman, with blue-highlighted user values, source citations on every clause, and a two-table audit appendix (clause sources + user input evidence). The chat response renders an interactive HTML artifact: hover any value to see the exact sentence it came from.

Three Pillars
Privacy

Self-contained, local-first deployment

API server, clause library, embeddings, and templates all run inside one isolated environment (Docker network or K8s namespace). Ollama runs on-device by default; Claude is opt-in. AI is confined to extraction — there's no path by which the model can inject text into the contract.

Reliability

Evidence-gated, conservative, deterministic

Every extracted value cites the user's own words. A missing field becomes a follow-up — never a guess. The system prefers three questions to one hallucination. Once fields are verified, template fill is reproducible byte-for-byte.

Scalability

Stateless tier, horizontal scale, provider-agnostic

Any pod can serve any request — containers are interchangeable. Demonstrated 4 pods serving 4 different contract types in 9 seconds wall time on Kubernetes. Swap Ollama ↔ Claude with one env variable, no code changes.

Key Design Decisions
Adopted

AI confined to extraction only

The model never writes contract text. All clause language comes from vetted templates (oneNDA, LawDepot, eForms, PandaDoc, FormSwift). Extraction populates a fixed schema; the assembler does the rest. No path exists for hallucinated language to reach the document.

Adopted

Evidence-gated extraction with composite scoring

Each extraction test is scored by a weighted composite: 50% follow-up coverage, 30% extraction accuracy, 20% no-hallucination (starts at 100%, –25% per invented field). Coverage is weighted highest because asking when uncertain is the safety behavior — the opposite of hallucination.

Rejected

Agent-owned questionnaire schema

Letting the LLM define field structure caused field-name drift, merged fields, and dropped requireds. The agent fills the schema — it doesn't own it. Schemas live in config/questionnaire_schema_*.json and are versioned with the codebase.

Adopted

OpenAI-compatible API surface

FastAPI exposes /v1/chat/completions with SSE streaming and session isolation, so any OpenAI-client UI works out of the box — Open WebUI is the default, but the integration surface is standard.

Adopted

Sticky routing for the demo, Redis as the production fix

Sessions live in pod memory. To stay simple under K8s, the demo routes a user back to the same pod across follow-ups. For production, the documented next step is a shared session store (Redis) so any pod can pick up where another left off.

Adopted

Embeddings always local

Even when Claude is the extraction provider, RAG embeddings (nomic-embed-text) stay on-device. Clause selection never round-trips through a cloud provider — keeps the clause library and selection logic inside the deployment boundary.
